## 引言：拆分是最后手段

技术讨论里常听到"数据量大了就分库分表"。这句话没错，但过于粗暴。分库分表确实能突破单机存储和连接瓶颈，代价却是查询能力、事务一致性和运维复杂度的全面上升。一旦拆错分片键或低估跨片查询的难度，团队会被复杂度拖垮。

正确的心态是：把分库分表当作"其他手段都用尽后"的最后一步。在拆之前，先把索引、SQL、缓存、读写分离、归档冷数据这些相对廉价的优化做扎实。很多所谓"扛不住"的系统，其实只是索引没建好或没做冷热分离。

## 什么时候才需要拆分

判断是否需要拆分，应基于可观测的信号，而非拍脑袋：

- 单表数据量达到千万级到亿级，且索引优化、SQL 优化后查询仍明显变慢；
- 数据库磁盘容量、IOPS 或连接数接近瓶颈，纵向扩容（加内存、换 SSD）已到天花板或成本过高；
- 写入并发高到单库锁竞争严重，影响正常业务。

即便满足这些条件，也要先问：能否通过归档历史数据、冷热分离、加缓存来缓解？只有当这些手段都无效，拆分才进入视野。记住一条原则：能不拆就不拆，能晚拆就晚拆。

## 垂直拆分与水平拆分

**垂直拆分**按列或业务拆分：把不常用或大字段拆到别的表（垂直分表），或把不同业务模块的表拆到不同库（垂直分库）。它能减少单行宽度、降低业务间锁竞争，但无法解决单表数据量过大的根本问题。

**水平拆分**按行拆分：把一张大表的数据按规则分散到多张结构相同的表或多个库中，每张表只存一部分数据。这才是应对海量数据的核心手段，但也是复杂性之源。水平拆分又分库内分表和分库，两者常结合使用。

## 分片键的选择

分片键（sharding key）决定了数据如何分布，是拆分中最关键、最难更改的决策。选择原则：

- **高频查询字段优先**：绝大多数查询都带上它，才能把查询路由到单一分片。例如订单表按 `user_id` 分片，用户查自己的订单就只扫一个片。
- **数据分布均匀**：避免热点。用自增 ID 取模分布均匀，但按时间分片容易造成写入集中。
- **避免跨片 JOIN**：关联紧密的表尽量用相同分片键，让相关数据落在同一片。

选错分片键的后果是灾难性的：如果查询经常不带分片键，就会退化成"广播查询"——扫所有分片再聚合，性能甚至不如拆分前。

## 跨片查询的难题

拆分后，原本简单的查询会变得棘手：

- **跨片 JOIN**：数据分散在不同库，无法直接 JOIN。常见做法是字段冗余、分批查询后在应用层拼装，或用宽表/搜索引擎兜底。
- **排序与分页**：跨片 `ORDER BY ... LIMIT` 需要各片取回数据后在中间件层归并排序，深分页（如 LIMIT 100000）开销极大。
- **聚合统计**：`COUNT`、`SUM` 等要下发到各片再汇总。

因此分片键的选择几乎决定了拆分后 80% 的查询体验。设计阶段就要梳理清楚核心查询模式，围绕它们设计分片策略。

## 分布式 ID：雪花算法

分表后不能再依赖单表的自增主键（各表会生成重复 ID），需要全局唯一的分布式 ID。雪花算法（Snowflake）是主流方案，它把 64 位整数划分为：符号位（1 位）+ 时间戳（41 位）+ 机器 ID（10 位）+ 序列号（12 位），保证不同机器、不同毫秒生成的 ID 不重复且大致递增。

```python
# 雪花算法核心逻辑（简化示意）
class Snowflake:
    def __init__(self, worker_id):
        self.worker_id = worker_id
        self.last_ms = 0
        self.seq = 0

    def next_id(self):
        ms = current_millis()
        if ms < self.last_ms:          # 时钟回拨，需特殊处理
            raise ClockBackwardError()
        if ms == self.last_ms:
            self.seq = (self.seq + 1) & 4095   # 12 位序列号
            if self.seq == 0:
                ms = wait_next_millis(self.last_ms)
        else:
            self.seq = 0
        self.last_ms = ms
        return ((ms << 22) | (self.worker_id << 12) | self.seq)
```

## 分片路由实现

应用或中间件根据分片键计算目标分片，下面是一个取模路由的示意：

```python
SHARD_COUNT = 4

def shard_for(user_id: int) -> str:
    """按 user_id 取模路由到分表"""
    idx = user_id % SHARD_COUNT
    return f"orders_{idx}"

def query_orders(user_id: int, sql: str):
    table = shard_for(user_id)
    # 必须带分片键，否则退化为广播查询
    return db.execute(sql.format(table=table))
```

```sql
-- user_id=10086 → 10086 % 4 = 2 → 查询 orders_2
SELECT * FROM orders_2 WHERE user_id = 10086 ORDER BY created_at DESC LIMIT 20;
```

工程上更推荐用成熟中间件（如 ShardingSphere、Vitess）或数据库自带的分布式方案，避免自研路由带来的边界问题。

## 踩坑与最佳实践

时钟回拨是雪花算法的经典坑：服务器时钟倒退会生成重复 ID，生产实现必须处理（等待、报警或借用序列号）。分片扩容也是大坑：从 4 片扩到 8 片，取模规则变化会导致大量数据需要迁移，因此初期要预留足够分片数，或采用一致性哈希降低迁移量。

另一个坑是事务：跨片事务无法使用本地事务，需引入分布式事务方案（如 XA、TCC、Seata），复杂度陡增。设计时应尽量让业务操作落在单一分片内。

## 小结

分库分表的时机信号是数据量与并发确实触及单机瓶颈、且常规优化已用尽。垂直拆分降耦合，水平拆分解数据量难题，而分片键的选择决定了拆分后的查询命运。它的代价是跨片 JOIN、排序分页、分布式 ID 和分布式事务的全面复杂化。记住：拆分不是终点而是新问题的起点，能靠索引、缓存、归档解决的，就别急着拆。
