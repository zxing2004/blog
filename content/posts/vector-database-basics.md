## 引言：从"关键词匹配"到"语义理解"

传统数据库擅长精确查询：找订单、查用户、按条件过滤。但面对"帮我找和这段话意思相近的文档"这类需求，关键词匹配就力不从心了——两段文字措辞不同却表达同一含义，倒排索引无法识别。向量数据库正是为解决这类"语义相似"检索而生。

随着大模型与 RAG（检索增强生成）的普及，向量数据库从研究成果变成了工程标配。它的核心任务很单纯：给一个向量，快速找出向量空间里和它最相似的一批向量。但要做到"海量数据下的快速"，背后涉及嵌入、索引、相似度度量等一整套机制。

## 向量嵌入与相似度

一切始于"嵌入（embedding）"。嵌入模型把文本、图片等非结构化数据映射成一串固定长度的浮点数——即向量。语义相近的内容，其向量在空间中的距离也相近。常见的文本嵌入维度在几百到几千维之间。

有了向量，就要定义"相似"。常用度量有：

- **余弦相似度（cosine）**：衡量两个向量夹角的余弦值，只关注方向、不受模长影响，文本场景最常用。
- **内积（inner product / dot）**：既考虑方向也考虑模长，在需要兼顾向量强度时使用。
- **欧氏距离（L2）**：衡量直线距离，几何意义直观。

选择哪种度量要与嵌入模型的训练目标一致，否则检索质量会打折扣。多数文本嵌入模型推荐余弦相似度。

## ANN 索引：HNSW 与 IVF

如果逐条计算查询向量与所有向量的相似度（精确搜索），数据量一大就无法接受。近似最近邻（ANN）索引通过牺牲极小的召回率换取数量级的速度提升，是向量数据库的核心。

**HNSW（Hierarchical Navigable Small World）**：构建多层图结构，上层是稀疏的"高速公路"，下层是稠密的近邻图。查询时从顶层入口出发，逐层贪心跳转到更接近目标的节点，最后在底层精修。HNSW 查询快、召回率高，但内存占用大、构建较慢。

**IVF（Inverted File Index）**：先用聚类算法把向量空间划成若干桶，查询时只在与查询向量最接近的几个桶里搜索，大幅缩小范围。IVF 内存友好、构建快，但召回率受聚类和搜索桶数影响，需要调参（如 `nlist`、`nprobe`）。

## 与 RAG 的关系

RAG 的典型流程是：知识文档切块 → 嵌入后存入向量库 → 用户提问时把问题也嵌入 → 检索相似片段 → 把片段连同问题喂给大模型生成答案。向量数据库在其中扮演"长期记忆"的角色，让模型能引用私有、最新的知识，缓解幻觉问题。

检索质量直接决定 RAG 效果的上限。嵌入模型选得是否合适、切块策略是否合理、索引参数是否调优，都会体现在最终答案里。

## 混合检索

纯向量检索也有短板：对精确匹配（如产品型号、专有名词、数字编号）反而不如关键词检索。于是出现了**混合检索**——同时跑向量检索和关键词（BM25）检索，再把两路结果融合排序（常用 RRF 倒数排名融合）。这样既保留语义泛化能力，又不丢精确匹配，是当下 RAG 系统的主流实践。

## 主流选型

- **Milvus**：分布式、性能强劲，面向大规模生产场景，支持 HNSW、IVF 等多种索引，运维相对复杂。
- **pgvector**：PostgreSQL 的扩展，让关系库直接支持向量存储与检索。优势是能与业务数据同库、用 SQL 联合查询，事务一致，运维成本低，非常适合已有 PG 的团队。
- **Chroma**：轻量、API 简洁，适合本地开发和小型项目快速上手。

对多数中小型场景，pgvector 是性价比极高的起点——不必引入新的基础设施。

## pgvector 实操

```sql
-- 安装扩展（需 DBA 权限，每个数据库执行一次）
CREATE EXTENSION IF NOT EXISTS vector;
```

```sql
-- 建表：embedding 为 1536 维向量（维度须与嵌入模型一致）
CREATE TABLE documents (
  id BIGSERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  content TEXT NOT NULL,
  embedding vector(1536) NOT NULL
);

-- 创建 HNSW 索引，相似度度量选余弦
CREATE INDEX ON documents
  USING hnsw (embedding vector_cosine_ops);
```

插入与查询（查询向量由嵌入模型生成，这里用占位示意）：

```sql
-- 插入一条带向量的文档（向量省略示意）
INSERT INTO documents (title, content, embedding)
VALUES ('向量数据库简介', '...', '[0.01,0.02,...]'::vector);

-- 相似检索：按余弦距离排序，取最相似的 10 条
-- <=> 是余弦距离运算符，距离越小越相似
SELECT id, title, 1 - (embedding <=> '[0.01,0.02,...]'::vector) AS similarity
FROM documents
ORDER BY embedding <=> '[0.01,0.02,...]'::vector
LIMIT 10;
```

Python 侧可用 `pgvector` 库把 numpy 数组转换为适配的字符串：

```python
from pgvector.psycopg import register_vector
import psycopg2, numpy as np

conn = psycopg2.connect(...)
register_vector(conn)
vec = np.array([0.01, 0.02, 0.03])  # 实际由嵌入模型生成
with conn.cursor() as cur:
    cur.execute(
        "SELECT id, title FROM documents "
        "ORDER BY embedding <=> %s LIMIT 10", (vec,)
    )
    print(cur.fetchall())
```

## 踩坑与最佳实践

维度必须与嵌入模型严格一致，换模型时存量向量要全部重新嵌入，这是常见的大坑。相似度度量要与模型匹配，用错度量会导致检索结果明显偏离预期。HNSW 虽快，但索引构建耗内存，导入大量数据时建议先建表导数据、后建索引。

另一个现实问题是"召回率 vs 延迟"的权衡：ANN 参数越激进越快，但可能漏掉正确结果。生产环境要用标注数据评估 Recall@K，不能只看响应速度。最后，别忘了混合检索——在很多业务里，加一路关键词检索带来的质量提升，比调半天向量索引参数更明显。

## 小结

向量数据库把"语义相似"变成可高效执行的检索：嵌入模型把内容映射为向量，余弦/内积等度量定义相似度，HNSW/IVF 等 ANN 索引解决海量数据下的速度问题。它在 RAG 中承担长期记忆的角色，而混合检索进一步补齐了精确匹配短板。选型上，大规模生产可考虑 Milvus，中小场景 pgvector 足够顺手。从维度、度量、索引参数到召回率评估，每个细节都影响最终效果，值得逐一打磨。
