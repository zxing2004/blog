## 当服务器"看起来很慢"时

凌晨两点，告警群里抛出一条消息：某台业务机器 P99 延迟从 50ms 跳到了 800ms，CPU 使用率却只有 40%。值班同学第一反应是"CPU 没满，应该不是计算问题"，于是开始翻应用日志，两小时毫无头绪。这种场景在运维中极其常见——性能问题很少会主动告诉你答案，它只会表现出一个模糊的症状。

更麻烦的是，很多人的排查停留在"敲几个命令看看数字"的层面：top 看一眼、free 看一眼，然后凭直觉猜。数字看到了，却不知道它意味着什么。真正缺的不是工具，而是一套方法论，把散落的工具串成一条可复现的排查链路。

## 用 USE 方法建立排查框架

 Brendan Gregg 提出的 USE 方法（Utilization 使用率、Saturation 饱和度、Errors 错误）是性能分析的事实标准。对每一类资源——CPU、内存、磁盘、网络——都问三个问题：它有多忙（U）？排队有多严重（S）？有没有出错（E）？先看饱和度往往比看使用率更有价值：CPU 使用率 40% 但运行队列很长，说明任务在等 CPU；磁盘利用率 100% 通常意味着已经饱和，因为磁盘是串行设备。

配合工具分层：`top`/`htop` 给全局概览，`vmstat` 看系统级上下文切换与内存，`iostat` 看磁盘，`pidstat` 下钻到进程。先看系统，再看进程，最后看代码级热点，逐层收窄。

## 常用命令与采样实操

先看整体与 CPU：

```bash
# 交互式概览，按 1 展开每个 CPU 核，H 看线程
top -H

# 每秒一次，共 5 次；关注 r（运行队列）、si/so（换页）、us/sy/wa/id
vmstat 1 5

# 每个进程的资源占用，1 秒粒度
pidstat -u -r -d -w 1
```

`vmstat` 里最容易被忽略的是 `r` 列（等待运行的进程数）和 `wa`（CPU 等待 IO 的时间占比）。若 `r` 长期超过 CPU 核数且 `wa` 高，瓶颈在磁盘而非 CPU。

磁盘与文件系统：

```bash
# 每 2 秒输出一次，共 3 次，显示扩展指标
iostat -xmdz 2 3

# 定位具体是哪个进程在读写磁盘
iotop -oP
```

`iostat -x` 重点看 `await`（平均 IO 等待毫秒数）、`util`（设备利用率百分比）和 `avgqu-sz`（队列长度）。`util` 接近 100% 即磁盘饱和，`await` 远高于正常值说明设备响应变慢。

拿到"哪个进程有问题"后，用 `perf` 定位到函数级热点，并生成火焰图：

```bash
# 对指定进程采样 30 秒，记录调用栈
perf record -F 99 -p <PID> -g -- sleep 30

# 查看热点函数
perf report --stdio

# 结合火焰图脚本生成可视化 SVG
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

火焰图里横向越宽的栈帧代表占用 CPU 时间越多，一眼就能找出"平顶"的热点函数。

当问题只在生产环境偶发、无法重启进程时，eBPF 的低开销动态追踪就派上用场。以 `bpftrace` 为例，统计内核函数耗时的分布：

```bash
# 统计 read 系统调用返回码，按进程名聚合
bpftrace -e 'tracepoint:syscalls:sys_exit_read /comm == "nginx"/ {
  @[comm, args->ret] = count();
}'

# 用 BCC 工具直接抓慢 IO（超过 10ms）
biosnoop -Q 10
```

eBPF 的优势是无需改代码、无需重启，探针按需注入内核，开销通常可控制在个位数百分比，非常适合线上"只此一次"的疑难杂症。

## 别漏掉网络这一环

USE 框架里的网络常常被漏掉，而很多"玄学延迟"恰恰藏在网卡层。用 `sar -n DEV 1` 观察每秒收发包量与吞吐量，用 `netstat -s` 查看重传、丢包统计，用 `ss -s` 看连接状态分布。当 CPU、内存、磁盘都正常但延迟抖动时，先看 `netstat -s | grep -i retrans`——若重传计数持续增长，说明链路质量或网卡缓冲有问题。容器的网络还要额外关注流量控制层的丢包：`tc -s qdisc show dev eth0` 能揭示是否触发了限速。把网络指标纳入同一张检查清单，才能避免"各项都正常却无从下手"的尴尬。

## 踩坑与最佳实践

日志记录命令本身也是证据。排查前先执行 `date`、`uptime`、`uname -a` 留存时间线与内核版本，事后复盘才对得上。

用 `pidstat`、iostat 时务必带上采样间隔和次数，单次快照极易误判——瞬时 100% 可能只是正常抖动。

`perf record -F 99` 的 99Hz 采样率是有意避开 100Hz 的定时器对齐，防止采样数据与系统节拍共振产生偏差。

eBPF 虽强，但生产使用要评估内核版本（通常需要 4.x 以上）与 `CAP_BPF` 权限，且先在小流量环境验证探针开销，避免观测行为本身击穿服务。

## 小结

性能排查的顺序应当是：先 USE 框架定性，再用系统工具定资源，接着用 `perf` 定进程与函数，最后用 eBPF 做线上低开销验证。工具会迭代，但"先全局后局部、先饱和度后使用率、用数据代替猜测"的思路不会变。把这条链路固化成检查清单，下次告警时你就能从容地一步步逼近真相，而不是凭运气瞎猜。
